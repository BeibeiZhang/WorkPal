Workflow 工作流Workflow

工作流将多个操作组合为可复用、可预测的流程。在 Agent 场景中，它以用户构建的流程链和 Agent 自主生成的任务步骤两种形式出现。Workflows combine multiple actions into reusable, predictable processes. In agent scenarios, they appear in two forms: user-built process chains and agent-generated task steps.

Surface · 流程

概述Overview

工作流减少碎片化——不同团队不再各自编写 prompt，而是由单一流程定义者为所有人设定步骤，这些流程可被复用、改编或模板化。工作流的使用还改善了数据在系统间流动的控制方式，prompt 可以从第三方工具拉取信息、进行转换，然后传递给序列中的下一阶段。Workflows reduce fragmentation — instead of different teams writing their own prompts, a single process author defines steps for everyone. These processes can be reused, adapted, or templatized. Workflows also improve how data flows between systems, as prompts can pull information from third-party tools, transform it, and pass it to the next stage.

💡
Agent 场景下的双模式Dual Modes for Agents
随着 Agent 能力增长，工作流界面需要同时支持 「编排模式 Authoring」（用户定义可复用流程）和 「报告模式 Reporting」（Agent 展示自己的逻辑供用户审查或修改）。As agent capabilities grow, workflow interfaces need to support both "Authoring Mode" (users define reusable processes) and "Reporting Mode" (agents present their logic for user review or modification).

工作流操作类型Workflow Actions

综合 / 摘要Synthesize / Summarize
合成或总结信息，需考虑引用和参考来源的传递以便验证。Synthesize or summarize information, with consideration for passing citations and references for verification.
重塑 / 重构Reshape / Restructure
确保工作流有足够的上下文和参考来定义最终输出的目标样式。Ensure the workflow has sufficient context and references to define the target style of the final output.
媒介转换Media Conversion
可以是简单转换（语音转文字），也可以是复杂操作（构建图片）。Can be simple conversions (speech-to-text) or complex operations (image generation).
验证细节Verify Details
添加显式步骤让用户在发送或分享前验证生成内容的形式或实质。Add explicit steps for users to verify the form or substance of generated content before sending or sharing.

最佳实践Best Practices

✓ Do
允许用户用自然语言描述意图，AI 据此生成结构化流程草稿供编辑。清晰区分人类创建的步骤和 Agent 生成的步骤。Allow users to describe intent in natural language, then AI generates a structured process draft for editing. Clearly distinguish between human-created and agent-generated steps.
✗ Don't
不要隐藏工作流的执行成本（token 用量、API 调用次数）。不要在执行失败后强制用户从头重启整个流程。Don't hide workflow execution costs (token usage, API call counts). Don't force users to restart the entire process from scratch after a failure.
✓ Do
当工作流涉及外部平台交互时（发送邮件、写入数据库），明确显示数据去向、目标端点和授权方式。When workflows involve external platform interactions (sending emails, writing to databases), clearly show data destinations, target endpoints, and authorization methods.
✗ Don't
不要让 Agent 构建的步骤与用户手动创建的步骤在视觉上无法区分——混合归属是信任流失的根源。Don't make agent-built steps visually indistinguishable from user-created ones — mixed attribution is the root cause of trust erosion.

设计要点Design Considerations

  • 1
    锚定用户意图Anchor in User Intent
    允许用户从自然语言描述出发，然后起草一个用户可以编辑的结构化流程。Allow users to start from natural language descriptions, then draft a structured process they can edit.
  • 2
    暴露执行成本Expose Execution Costs
    在工作流和步骤层级展示预估的 token 用量、运行时间或 API 调用次数。Show estimated token usage, runtime, or API call counts at both workflow and step levels.
  • 3
    步骤级验证Step-Level Validation
    提供测试或采样输出选项，允许在不提交完整流程的情况下快速验证。Provide test or sample output options, allowing quick validation without committing to the full workflow.
  • 4
    标记步骤归属Mark Ownership
    视觉标记、分组或标签区分用户创建的步骤和 Agent 生成的步骤。Use visual markers, grouping, or labels to distinguish user-created steps from agent-generated ones.
  • 5
    可配置检查点Configurable Checkpoints
    长时间运行或高风险的工作流需要设置 Agent 主动让渡控制权给人类的门控。Long-running or high-risk workflows need gates where agents proactively hand control back to humans.
  • 6
    内联干预Inline Intervention
    允许用户暂停、跳过或就地调整参数，从修改点继续而非强制重启。Allow users to pause, skip, or adjust parameters in place, continuing from the modification point instead of forcing a restart.
  • 7
    标注跨系统边界Cross-System Boundaries
    明确高亮所有涉及外部平台的数据传递，展示数据去向和权限信息。Clearly highlight all data transfers involving external platforms, showing data destinations and permission information.
  • 8
    展示推理过程Expose Reasoning
    当 AI 自行构建工作流时，确保每个步骤附带元数据描述其选择原因。When AI builds workflows on its own, ensure each step includes metadata describing why it was chosen.

Action Plan 行动计划Action Plan

当 AI 承担复杂任务时，行动计划提供关键检查点——AI 在执行前先展示其计划步骤，给用户确认或调整的机会，让执行透明且可预测。When AI takes on complex tasks, action plans provide critical checkpoints — AI presents its planned steps before execution, giving users the opportunity to confirm or adjust, making execution transparent and predictable.

Governor · 治理层

概述Overview

Action Plan 的核心权衡在于速度与安全：确认步骤增加了延迟，但也在高风险领域充当了安全阀。设计者需要校准阈值——何时阻塞进度直到计划被批准，何时只是展示思维链作为参考。The core trade-off of Action Plans is speed vs. safety: confirmation steps add latency, but also serve as safety valves in high-risk areas. Designers need to calibrate thresholds — when to block progress until a plan is approved, and when to simply display the chain of thought as reference.

变体形式 Variants

步骤列表Step Lists
线性动作大纲，需快速确认。如 Claude Projects 生成前展示步骤。Linear action outlines requiring quick confirmation. E.g., Claude Projects showing steps before generation.
执行预览Execution Previews
与代码/自动化关联，带显式审批门控。如 Replit、Devin。Linked to code/automation, with explicit approval gates. E.g., Replit, Devin.
内容大纲Content Outlines
文档骨架，可选确认。如 Gamma 展示大纲但不阻塞生成。Document skeletons with optional confirmation. E.g., Gamma shows outlines without blocking generation.
自适应计划Adaptive Plans
过程中演化的计划。如 Perplexity Labs 随信息源变化调整。Plans that evolve during execution. E.g., Perplexity Labs adapts as information sources change.

最佳实践Best Practices

✓ Do
保持计划可浏览性——用户应在几秒内理解意图。允许对单个步骤进行编辑和纠错，而非要求重新生成整个计划。Keep plans skimmable — users should understand intent within seconds. Allow editing and correction of individual steps rather than requiring full plan regeneration.
✗ Don't
不要让执行无声地偏离计划——如果偏差发生必须更新或解释。不要将计划作为纯装饰展示而无法修改。Don't let execution silently deviate from the plan — deviations must be updated or explained. Don't display plans as pure decoration that can't be modified.

设计要点Design Considerations

  • 1
    可浏览性Keep Plans Skimmable
    用户应该能在几秒内理解计划意图，避免过于冗长的技术细节。Users should understand plan intent within seconds, avoiding overly verbose technical details.
  • 2
    支持局部编辑Make Plans Modifiable
    允许用户针对单个步骤编辑和纠错，提供有针对性的工具来发现和修正错误。Allow users to edit and correct individual steps, providing targeted tools for finding and fixing errors.
  • 3
    计划执行保真度Plan-Execution Fidelity
    计划只有在系统忠实执行时才有价值。无声的偏差会快速侵蚀信任。Plans are only valuable when the system faithfully executes them. Silent deviations quickly erode trust.
  • 4
    允许折叠/跳过Let Users Collapse or Bypass
    经验丰富的用户信任系统后更重视速度，但始终保留查看计划的入口。Experienced users who trust the system prioritize speed, but always preserve access to view plans.

Stream of Thought 思维链Stream of Thought

展示 AI 从输入到输出的可见轨迹——包括制定的计划、调用的工具、执行的代码，以及做出的决策。让系统更易读、更值得信任。Display AI's visible trail from input to output — including plans formulated, tools invoked, code executed, and decisions made. Making the system more readable and trustworthy.

Governor · 治理层

概述Overview

Stream of Thought 揭示了 AI 如何从输入导航到答案的可见轨迹。这可能包括它形成的计划、调用的工具、代表你执行的代码，以及沿途做出的检查和决策。

三种表达形式Three Expressions

人类可读计划Human-Readable Plans
预览 AI 将要做什么，让用户在执行前了解意图。Preview what AI will do, letting users understand intent before execution.
执行日志Execution Logs
记录工具调用、代码执行和结果的详细审计轨迹。Detailed audit trail of tool calls, code execution, and results.
紧凑摘要Compact Summaries
精简总结逻辑推理和关键决策点。Concise summaries of logical reasoning and key decision points.

最佳实践Best Practices

✓ Do
将思维链显示在有边界的容器中，默认折叠。根据任务复杂度调整可见性深度——简单对话需要少量展示，复杂任务需要完整轨迹。Display chain of thought in bounded containers, collapsed by default. Adjust visibility depth based on task complexity — simple conversations need minimal display, complex tasks need full trails.
✗ Don't
不要让思维链信息淹没主要输出内容。不要在用户无法暂停或停止 AI 处理的情况下展示实时思考过程。Don't let chain of thought information overwhelm the main output. Don't show real-time thinking processes when users can't pause or stop AI processing.

设计要点Design Considerations

  • 1
    有界容器Bounded Display
    使用可折叠的区域展示思维过程，避免与最终输出混淆。Use collapsible areas to display thought processes, avoiding confusion with final output.
  • 2
    渐进式披露Progressive Disclosure
    提供概要层和详情层，让用户按需深入，不被一次性展示的信息淹没。Provide summary and detail layers, allowing users to dive deeper as needed without being overwhelmed.
  • 3
    保持用户控制User Agency
    允许用户在处理过程中查看思维链，并提供停止、暂停、修改的控制。Allow users to view chain of thought during processing, with controls to stop, pause, and modify.

Verification 验证确认Verification

AI 越来越独立地运行。伴随自主性而来的是错误决定可能产生负面后果的关键时刻。验证模式根据潜在危害、范围和可逆性来匹配摩擦力度。AI operates increasingly independently. With autonomy come critical moments where wrong decisions can have negative consequences. Verification patterns match friction levels to potential harm, scope, and reversibility.

Governor · 治理层

核心原则Core Principle

⚖️
摩擦力匹配风险 Match Friction to Risk
高影响力或不可逆的操作需要强确认机制；常规或可轻松撤销的任务使用轻量检查。关键是根据操作的潜在危害、范围和可逆性来校准验证力度。High-impact or irreversible operations need strong confirmation mechanisms; routine or easily undone tasks use lightweight checks. The key is calibrating verification intensity based on potential harm, scope, and reversibility.

风险等级对照Risk Matrix

风险等级 操作示例 验证方式
🟢 低风险 搜索、浏览、草稿编辑 无需验证
🟡 中风险 内容修改、文件重命名 行内确认（Accept/Reject）
🟠 高风险 发送邮件、提交表单 带预览的模态确认
🔴 关键风险 支付、删除数据、API 写入 多步验证 + 撤销窗口

最佳实践Best Practices

✓ Do
对高影响力操作默认启用验证。允许用户通过设置跳过，但确保跳过时有明确的风险提示。Enable verification by default for high-impact operations. Allow users to skip via settings, but ensure clear risk warnings when skipping.
✗ Don't
不要对低风险操作（搜索、浏览）添加验证——过度确认会训练用户条件反射地点击"确认"，反而降低安全性。Don't add verification to low-risk operations (search, browse) — over-confirmation trains users to reflexively click "confirm", actually reducing security.

Memory 记忆系统Memory

赋予 AI 跨交互保留和复用信息的能力，系统可以回忆先前的上下文、偏好或事实——将 AI 从事务性工具转变为持久的个人助手。Empowering AI to retain and reuse information across interactions, the system can recall prior context, preferences, or facts — transforming AI from a transactional tool into a persistent personal assistant.

Governor · 治理层

设计要点Design Considerations

  • 1
    记忆绝不能是黑箱Never a Black Box
    当新记忆被添加时应通知用户，展示 AI 记住了什么以及这些记忆如何影响输出。Users should be notified when new memories are added, showing what AI remembers and how those memories affect output.
  • 2
    可管理和控制Manageable & Controllable
    让用户轻松查看、编辑、锁定重要信息以及清除不正确或敏感的记忆。Let users easily view, edit, lock important information, and clear incorrect or sensitive memories.
  • 3
    知识图谱Knowledge Map
    展示已保留信息及其对输出的影响关系，使记忆系统的运作方式一目了然。Display retained information and its impact relationships on output, making the memory system's operation clear at a glance.
  • 4
    适当的作用域Scope Appropriately
    不是所有记忆都应是全局的——支持项目级、工作区级和对话级的记忆保留。Not all memories should be global — support project-level, workspace-level, and conversation-level memory retention.
  • 5
    支持遗忘和保存Forgetting & Saving
    支持清除不正确/敏感信息（遗忘）和锁定重要事实（显式保存）两种操作。Support both clearing incorrect/sensitive information (forgetting) and locking important facts (explicit saving).

Connectors 连接器Connectors

设计良好的连接器让作用域显而易见：哪些数据源已连接、适用什么权限、AI 是在读取内容还是在执行修改。Well-designed connectors make scope obvious: which data sources are connected, what permissions apply, and whether AI is reading content or making modifications.

Tuner · 调节器

三种连接场景Where Connectors Appear

账户级同步Account-Level Sync
索引数据源用于对话问答，如 ChatGPT 的 Google Drive 集成。Index data sources for conversational Q&A, e.g., ChatGPT's Google Drive integration.
应用侧边栏App Sidebar
从应用套件中拉取上下文，如 Gemini 在 Gmail/Docs 中。Pull context from app suites, e.g., Gemini within Gmail/Docs.
企业级连接器Enterprise Connectors
管理员配置的组织级连接，如 Microsoft Graph。Admin-configured organization-level connections, e.g., Microsoft Graph.
⚠️
安全警示：隐藏指令风险Security Alert: Hidden Instruction Risk
AI 读取内容时可能遇到邮件、日历、文档中嵌入的隐藏指令。设计时应先解析和摘要，再将工具操作置于用户明确意图之后。当模型即将根据检索内容中的指令行动时，必须展示人类可读预览并要求确认。AI may encounter hidden instructions embedded in emails, calendars, and documents when reading content. Design should parse and summarize first, then place tool actions behind explicit user intent. When the model is about to act on instructions from retrieved content, it must show a human-readable preview and request confirmation.

设计要点Design Considerations

  • 1
    数据源选择器Source Pickers
    允许用户精确控制 AI 可以访问哪些工作区、频道或文件夹。Allow users precise control over which workspaces, channels, or folders AI can access.

Inspector Panel 检查面板Inspector Panel

当 Agent 在后台执行多步任务时，检查面板作为持久化侧边栏，实时展示任务进度、可用工具、文件产出和上下文来源——让用户在不打断 Agent 工作的前提下保持态势感知。When agents execute multi-step tasks in the background, the inspector panel serves as a persistent sidebar, displaying task progress, available tools, file outputs, and context sources in real time — keeping users situationally aware without interrupting agent work.

Surface · 运维Operations

概述Overview

检查面板是 Agent 运行时的「仪表侧栏」。传统聊天界面仅展示对话流，但当 Agent 调用工具、生成文件、连接外部服务时，用户需要一个结构化的视图来了解当前状态。检查面板将这些元信息从对话流中抽离，以独立面板的形式常驻，使用户能一眼掌握 Agent 正在做什么、已经完成了什么、手头有哪些资源。The inspector panel is a "dashboard sidebar" for agent runtime. Traditional chat interfaces only show conversation flow, but when agents invoke tools, generate files, and connect to external services, users need a structured view of the current state. The inspector panel extracts this meta-information from the conversation flow into a persistent independent panel, enabling users to grasp at a glance what the agent is doing, what it has completed, and what resources it has at hand.

💡
设计定位：伴随而非取代Design Position: Accompany, Not Replace
检查面板不替代对话界面，而是作为补充——用户在对话中与 Agent 互动、下达指令，同时通过检查面板监控全局状态。两者互补而非互斥。The inspector panel doesn't replace the conversation interface but supplements it — users interact with agents and give instructions through conversation while monitoring overall status through the inspector panel. The two complement rather than compete with each other.

核心模块Core Modules

📋 任务进度 Progress📋 Task Progress
带百分比和状态图标的任务清单，展示已完成、进行中和待处理的步骤。Task checklist with percentages and status icons, showing completed, in-progress, and pending steps.
📂 文件产出 Outputs📂 File Outputs
Agent 生成的文件列表，支持直接预览、下载或在关联应用中打开。List of agent-generated files, supporting direct preview, download, or opening in associated applications.
🔌 上下文连接器 Context🔌 Context Connectors
当前已连接的数据源、MCP 服务器、浏览器扩展等外部工具的状态展示。Status display of currently connected data sources, MCP servers, browser extensions, and other external tools.
🛠️ 技能面板 Skills🛠️ Skills Panel
Agent 当前可用的技能和能力标签，帮助用户理解 Agent 的能力边界。Labels for currently available agent skills and capabilities, helping users understand agent capability boundaries.
📥 输入来源 Inputs📥 Input Sources
用户上传的文件、选中的文件夹和指令文件的引用列表。Reference list of user-uploaded files, selected folders, and instruction files.
🧠 记忆摘要 Memory🧠 Memory Summary
当前会话中 Agent 记住的关键上下文快照。Key context snapshots that the agent remembers in the current session.

最佳实践Best Practices

✓ Do
让任务进度实时更新，每完成一步立即反映。文件产出区域提供一键打开/下载操作，减少用户查找成本。Update task progress in real time, reflecting each completed step immediately. Provide one-click open/download for file outputs, reducing user search costs.
✗ Don't
不要让检查面板占据过多屏幕空间——它应该是可折叠的辅助视图。不要在面板中重复对话内容，保持信息的互补性。Don't let the inspector panel take up too much screen space — it should be a collapsible auxiliary view. Don't repeat conversation content in the panel — keep information complementary.
✓ Do
在连接器状态异常时（断开、权限不足）提供明确的视觉警告和重新连接入口。标注每个技能/工具的来源和版本。Provide clear visual warnings and reconnection entry points when connector status is abnormal (disconnected, insufficient permissions). Label the source and version of each skill/tool.
✗ Don't
不要混淆「进度」和「日志」——进度是用户关心的高层概要，日志是开发者级别的详细记录，两者应分层展示。Don't confuse "progress" with "logs" — progress is the high-level summary users care about, logs are developer-level detailed records. They should be displayed in separate layers.

设计要点Design Considerations

  • 1
    持久化但不干扰Persistent but Non-Intrusive
    检查面板应始终可访问（侧边栏或底部抽屉），但不强制显示。用户可以选择何时查看，何时收起。The inspector panel should always be accessible (sidebar or bottom drawer) but not forced to display. Users choose when to view and when to collapse.
  • 2
    分区清晰的信息架构Clear Information Architecture
    进度、文件、连接器、技能等模块应有明确的视觉分区。每个模块可独立折叠/展开，避免信息过载。Progress, files, connectors, skills, and other modules should have clear visual separation. Each module can be independently collapsed/expanded to avoid information overload.
  • 3
    可操作的文件卡片Actionable File Cards
    产出文件不应只是列表——提供预览缩略图、文件类型图标、大小信息，以及一键打开/下载/分享的操作。Output files shouldn't just be a list — provide preview thumbnails, file type icons, size information, and one-click open/download/share actions.
  • 4
    连接状态的实时反馈Real-Time Connection Status Feedback
    外部连接器的在线/离线/错误状态应使用颜色编码实时展示。断开时提供内联重连操作，而非跳转到设置页。Online/offline/error status of external connectors should be displayed in real time using color coding. When disconnected, provide inline reconnection actions rather than navigating to settings.
  • 5
    进度与预期管理Progress and Expectation Management
    除了完成百分比，还应展示预估剩余时间或步骤数。当 Agent 陷入重试或意外暂停时，进度条应明确反映异常状态。Beyond completion percentage, show estimated remaining time or step count. When agents enter retry loops or unexpected pauses, the progress bar should clearly reflect abnormal status.
  • 6
    技能透明度Skill Transparency
    展示 Agent 当前加载的技能/插件列表，让用户理解为什么 Agent 能（或不能）处理某些类型的任务。Display the list of currently loaded agent skills/plugins, helping users understand why agents can (or cannot) handle certain types of tasks.

Operations Dashboard 运营仪表盘Operations Dashboard

当组织运行多个 Agent 时，需要一个全局控制中心——监控系统健康度、AI 用量与成本、任务队列、Worker 状态和预算风险，让运维团队在单一视图中掌控 Agent 集群的全貌。When organizations run multiple agents, they need a global control center — monitoring system health, AI usage and costs, task queues, worker status, and budget risks, giving operations teams a complete view of the agent fleet in a single view.

Governor · 运维Operations

概述Overview

运营仪表盘是 Agent 系统的「指挥中心」。当 Agent 从单一助手扩展为多实例集群——多个 Worker 并行执行不同任务、消耗不同量级的 Token、连接不同的外部服务——管理者需要一个全局视图来回答四个核心问题：系统是否正常？哪里需要人工介入？谁在忙？AI 用量是否在预算内？The operations dashboard is the "command center" for agent systems. When agents scale from a single assistant to multi-instance clusters — multiple workers executing different tasks in parallel, consuming varying amounts of tokens, connecting to different external services — managers need a global view to answer four core questions: Is the system healthy? Where does human intervention needed? Who is busy? Is AI usage within budget?

⚠️
从个人工具到组织基础设施From Personal Tool to Organizational Infrastructure
随着 Agent 从个人助手演变为企业级基础设施，仪表盘设计需要同时服务两类用户：日常操作者（关注当前任务和即时问题）和 管理者/运维（关注趋势、成本和系统级健康度）。单一仪表盘需要通过信息层级和视图切换来满足双重需求。As agents evolve from personal assistants to enterprise infrastructure, dashboard design needs to serve two user types: daily operators (focused on current tasks and immediate issues) and managers/operations (focused on trends, costs, and system-level health). A single dashboard needs information hierarchy and view switching to meet both needs.

核心仪表盘模块Core Dashboard Modules

🟢 系统健康度 Health Score🟢 System Health Score
综合评分（如 100 分制）汇总审核队列、运行异常、停滞执行和预算风险，一眼判断系统状态。Composite score (e.g., out of 100) summarizing review queues, runtime anomalies, stalled executions, and budget risks for instant system assessment.
📊 AI 用量追踪 Usage Tracking📊 AI Usage Tracking
Token 消耗量、预估费用、请求次数的实时计数和趋势图表，带预算阈值警告。Real-time counts and trend charts for token consumption, estimated costs, and request counts, with budget threshold warnings.
👥 Worker 状态 Worker Status👥 Worker Status
每个 Agent Worker 的当前任务、会话数、Cron 任务数、最后活跃时间和实时/离线状态。Each agent worker's current task, session count, cron job count, last active time, and online/offline status.
🚨 需要介入 Needs Attention🚨 Needs Attention
聚合所有需要人工审核、被阻塞或触发风险规则的事项到一个「待办」视图。Aggregate all items needing human review, blocked tasks, or triggered risk rules into a single "to-do" view.
📅 任务排程 Task Scheduling📅 Task Scheduling
下一批 Cron 任务、定时心跳和计划执行的时间线视图。Timeline view of upcoming cron tasks, scheduled heartbeats, and planned executions.
💰 预算与订阅 Budget & Billing💰 Budget & Billing
AI 费用占预算比例、用量趋势、剩余额度和超支预警的财务视图。Financial view showing AI cost-to-budget ratio, usage trends, remaining quota, and overspend alerts.

最佳实践Best Practices

✓ Do
首屏聚焦「四个核心问题」——系统健康吗？哪里需要我介入？谁在忙？费用安全吗？进阶信息放在二级视图。Focus the first screen on "four core questions" — Is the system healthy? Where do I need to intervene? Who is busy? Is spending safe? Advanced info goes in secondary views.
✗ Don't
不要在仪表盘首屏堆砌原始日志或低层级指标——管理者需要汇总和趋势，不是逐行日志。不要让健康评分成为不可解释的黑箱数字。Don't pile raw logs or low-level metrics on the dashboard's first screen — managers need summaries and trends, not line-by-line logs. Don't let health scores become unexplainable black-box numbers.
✓ Do
为每个 Worker 提供快速入口查看其当前任务详情和对话历史。预算数据要实时且带趋势预测——不只是当前费用，还要预估月底费用。Provide quick entry for each worker to view current task details and conversation history. Budget data should be real-time with trend forecasting — not just current costs, but projected end-of-month costs.
✗ Don't
不要让「需要介入」的通知淹没在其他信息中——这是仪表盘最重要的信号，应有最高优先级的视觉权重。Don't let "needs attention" notifications drown in other information — this is the dashboard's most important signal and should have the highest visual priority.

设计要点Design Considerations

  • 1
    健康评分可解释Explainable Health Scores
    综合健康分数下方应拆解为子指标（审核队列 0、运行异常 0、停滞执行 0、预算风险 0），让用户快速定位问题来源。Below the composite health score, break down into sub-metrics (review queue 0, runtime anomalies 0, stalled executions 0, budget risk 0), enabling users to quickly locate problem sources.
  • 2
    多语言与本地化Multilingual & Localization
    Agent 运营团队可能分布全球，仪表盘应支持语言切换，并使用 locale-aware 的日期/时间/货币格式。Agent operations teams may be globally distributed. Dashboards should support language switching and use locale-aware date/time/currency formats.
  • 3
    实时 vs. 定期刷新Real-Time vs. Periodic Refresh
    关键指标（健康分、需要介入数）应使用 WebSocket 实时推送；历史趋势和汇总报表可定期刷新以减轻服务器压力。Critical metrics (health score, attention-needed count) should use WebSocket real-time push; historical trends and summary reports can refresh periodically to reduce server load.
  • 4
    从概览到详情的钻取Overview-to-Detail Drill-Down
    仪表盘的每个卡片都应支持点击钻取——从概要数字进入详情列表，再从列表进入单个任务/Worker/会话的完整视图。Every card on the dashboard should support click-through drill-down — from summary numbers to detail lists, then from lists to the full view of individual tasks/workers/sessions.
  • 5
    预算护栏与告警Budget Guardrails & Alerts
    支持设置预算阈值（如日限/月限），接近阈值时渐变警告（黄→橙→红），超出时自动暂停低优先级任务并通知管理员。Support budget threshold settings (e.g., daily/monthly limits), gradient warnings when approaching thresholds (yellow→orange→red), and automatic low-priority task suspension with admin notification when exceeded.
  • 6
    多 Agent 身份区分Multi-Agent Identity Distinction
    每个 Agent Worker 应有独特的名称、头像或颜色标识，让运维人员在密集的任务列表中快速辨认是哪个 Agent 在执行。Each agent worker should have a unique name, avatar, or color identifier, enabling operations staff to quickly identify which agent is executing in dense task lists.
  • 7
    审计日志与回溯Audit Logs & Retrospection
    仪表盘应保留历史快照，支持回溯到任意时间点查看当时的系统状态、活跃 Agent 和执行记录。Dashboards should retain historical snapshots, supporting retrospection to any point in time to view system state, active agents, and execution records.

Supports filtering by model and workspace with CSV export. A standard implementation of platform-level API usage monitoring.
A
Anthropic Console · 2025.06
费用与账单视图——按模型拆分的费用明细、每日成本趋势、预估月度账单。设置支出限额并在接近阈值时告警，对应仪表盘的「预算与订阅」模块，实现预算护栏的可视化管理。Cost and billing view — cost breakdown by model, daily cost trends, projected monthly bills. Set spending limits with threshold alerts, implementing visual budget guardrail management.
A
Anthropic Console · 2025.06
速率限制监控——实时展示被限流的请求数量和趋势，帮助运维团队识别流量峰值和容量瓶颈。对应仪表盘「系统健康度」子指标中的异常监测模块。Rate limit monitoring — real-time display of rate-limited request counts and trends, helping ops teams identify traffic spikes and capacity bottlenecks. Corresponds to anomaly detection in the "System Health" sub-metrics.

"Pause" and "Stop" buttons provide immediate intervention capability, a typical implementation of the "Needs Attention" module.

用量追踪仪表盘——实时展示字符消耗量、剩余额度和用量趋势图。进度条式的额度可视化（已用/总量）是「预算护栏」最直观的交互模式。Usage tracking dashboard — real-time display of character consumption, remaining quota, and usage trends. Progress-bar quota visualization (used/total) is the most intuitive interaction pattern for "budget guardrails".
F
Flora Fauna · 2025.03
操作前费用预估与确认——在执行高成本 AI 操作前展示预估费用并要求用户确认。这种「确认门」机制是预算护栏的前置防线：在资源消耗之前拦截，而非事后补救。Pre-operation cost estimation and confirmation — shows estimated cost before high-cost AI operations and requires user confirmation. This "confirmation gate" mechanism is a proactive budget guardrail: intercepting before resource consumption, not remediating after.
